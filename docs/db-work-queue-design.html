DB Work Queue

A Db2 table as a work queue: lease a row, run the job, write the outcome fenced on the attempt.
Two Java files, three SQL statements, no coordinator.

Architecture

Key design decisions

No coordinator

No broker, no membership, no sweeper. SKIP LOCKED DATA lets competing workers pass over each other's rows instead of waiting.

A lease, not a held lock

The claim commits at once. No lock or connection is held while the handler runs; ownership ends when AVAILABLE_AT passes.

Fenced outcomes

ATTEMPTS rises with every claim and is never reset. Outcome writes require this claim's value, so a stale worker's write updates 0 rows (and is logged).

At-least-once

A crash after the handler, or a handler that outlives its lease, runs the job again. Handlers must be idempotent on operationId.

Virtual threads

One virtual thread per worker and one per running handler, so blocking JDBC and downstream calls cost no platform thread. workers still caps concurrency.

The core: three SQL statements

This is all the SQL in WorkQueue.java. Recovery from crashes needs no statement of its own.

1. CLAIM: lease the oldest available row

SELECT ID, OPERATION_ID, PAYLOAD, ATTEMPTS FROM FINAL TABLE (
  UPDATE (SELECT ID, OPERATION_ID, PAYLOAD, STATUS, ATTEMPTS, AVAILABLE_AT FROM WORK_ITEM
           WHERE AVAILABLE_AT <= CURRENT TIMESTAMP ORDER BY AVAILABLE_AT FETCH FIRST 1 ROW ONLY)
     SET STATUS = 'CLAIMED', ATTEMPTS = ATTEMPTS + 1,
         AVAILABLE_AT = CURRENT TIMESTAMP + CAST(:lease AS DECIMAL(18, 3)) SECONDS)
SKIP LOCKED DATA

Why it's safe: select, update and read-back are one statement, and rows another claimer has locked are skipped, so two workers never take the same row. AVAILABLE_AT <= now matches new rows, retries whose backoff is over, and CLAIMED rows whose lease ran out, which is how crashed work comes back. The returned ATTEMPTS is this claim's fencing token.

2. RETRY: the handler failed and attempts are left

UPDATE WORK_ITEM
   SET STATUS = 'PENDING', LAST_ERROR = :error,
       AVAILABLE_AT = CURRENT TIMESTAMP + CAST(:backoff AS DECIMAL(18, 3)) SECONDS
 WHERE ID = :id AND ATTEMPTS = :attempts AND STATUS = 'CLAIMED'

3. FINISH: DONE, or FAILED on the last attempt

UPDATE WORK_ITEM
   SET STATUS = :status, LAST_ERROR = :error, AVAILABLE_AT = NULL
 WHERE ID = :id AND ATTEMPTS = :attempts AND STATUS = 'CLAIMED'

Why it's safe: if the lease ran out and another worker claimed the row, ATTEMPTS has moved on and the write updates 0 rows. The worker logs that it lost its lease and moves to the next job.

Invariants

  • ATTEMPTS only goes up. Each claim gets a value no other claim of that row ever had.
  • AVAILABLE_AT is NULL exactly when the row is finished. A CHECK enforces it, and finished rows never match the claim.
  • The lease is the handler's timeout. A handler still running when it ends is interrupted and the attempt fails.

The fence at work: if B wakes up afterwards and writes its outcome, the write requires ATTEMPTS = 2 and so changes nothing. If C had crashed too, the next claim would set ATTEMPTS = 4, see it is past max-attempts, and write FAILED.

The lease is also the handler's timeout

  • A handler that stops when interrupted gets its outcome written while the row is still its own.
  • A handler that ignores the interrupt keeps its worker busy. Once Db2's lease ends, another worker can run the job again, and the old outcome write updates 0 rows.
  • If claiming itself took the whole lease, the handler is not started. The row waits out its lease as if the worker had crashed.

Db2 must run in UTC. Leases and backoffs use only the database clock, so app machines' clocks don't matter. But CURRENT TIMESTAMP is local time, and a daylight-saving change would shift every lease and backoff by an hour.

What happens when

EventResult
The handler throwsThe row is retried after retry-backoff. The last attempt sets FAILED with the error in LAST_ERROR.
The handler runs past the leaseIt is interrupted and the attempt fails with handler outlived its lease.
The handler ignores the interruptIts worker waits for it. Once the lease ends, another worker can run the job again, and the old outcome write updates 0 rows.
An instance is killed or its machine diesIts rows stay CLAIMED until their leases end, then any instance claims them. Each costs one attempt.
An instance gets SIGTERMIt stops claiming and gives running handlers 30s. Handlers still running then are interrupted, which counts as a failed attempt. Rows it leaves CLAIMED run again after their lease.
The database is unreachableEach worker logs the error, sleeps poll-interval and tries again. A dead connection fails after 30s instead of hanging.
The handler succeeded but saving DONE failedThe row stays CLAIMED and runs again after its lease (at-least-once).
Two workers reach for the same rowThe second skips the locked row and takes the next available one. It sleeps only if nothing is left.
A producer enqueues the same OPERATION_ID twiceThe second insert fails with SQLSTATE 23505: the job is already enqueued.

Handlers must bound their downstream calls with timeouts and stop when interrupted. workers is a hard concurrency limit. If every worker on an instance is stuck, that instance stops claiming and its rows wait for a free worker on another instance. More workers only delay the stall.

Choosing values

lease

Longer than your slowest legitimate job plus the claim. Too short: slow jobs are interrupted until they fail. Too long: a crashed job waits that long to run again.

max-attempts × retry-backoff

A job that always fails reaches FAILED after about (max-attempts − 1) × retry-backoff plus its run time: about 2 minutes with the defaults.

poll-interval

An idle instance sends workers / poll-interval claims per second, 16 by default. A busy worker claims its next job at once.

workers and the pool

A worker holds a connection only for one statement, so Hikari's default pool of 10 is enough for the queue. Add a connection per worker if the handler uses the same pool.

Limits

  • Order is roughly oldest AVAILABLE_AT first, not FIFO. Retries move to the back, and there are no priorities.
  • One lease for every job. A job that needs more time than the others needs its own queue.
  • DONE and FAILED rows stay: they record that an OPERATION_ID was enqueued. Deleting one lets that ID be enqueued again.

Evolution: from engine to one class

The first design (spec dated 2026-09-21, now deprecated) kept claims alive by renewing them and ran background loops to clean up. The redesign drops every loop except the worker's, by making the lease the timeout and the next claim the cleanup.

Both designs rejected bucket ownership with a membership table (rebalancing, skew) and Spring Batch remote partitioning (partitions fixed at step start).

Run and check

  1. Apply schema.sql to a Db2 that runs in UTC.
  2. Put your job in the handler in App.java. Throw to retry.
  3. Set SPRING_DATASOURCE_URL, SPRING_DATASOURCE_USERNAME and SPRING_DATASOURCE_PASSWORD.
  4. Run ./mvnw spring-boot:run on as many machines as you like. SIGTERM lets running jobs finish (up to 30s).

Producers enqueue with INSERT INTO WORK_ITEM (OPERATION_ID, PAYLOAD) VALUES (?, ?). A duplicate OPERATION_ID fails with SQLSTATE 23505: already enqueued.

Check what's in the queue

-- How many rows in each state
SELECT STATUS, COUNT(*) FROM WORK_ITEM GROUP BY STATUS;

-- Jobs that ran out of attempts, and why
SELECT OPERATION_ID, ATTEMPTS, LAST_ERROR FROM WORK_ITEM WHERE STATUS = 'FAILED';

-- How far behind the queue is: the oldest row that could be claimed right now
SELECT MIN(AVAILABLE_AT) FROM WORK_ITEM WHERE AVAILABLE_AT <= CURRENT TIMESTAMP;

-- Leases that ran out (crashed or hung workers), waiting for another worker
SELECT * FROM WORK_ITEM WHERE STATUS = 'CLAIMED' AND AVAILABLE_AT < CURRENT TIMESTAMP;

What the tests prove

./mvnw test runs against a real Db2 in Docker (a few minutes on Apple Silicon), because the claim relies on SKIP LOCKED DATA.

  • Three instances share 300 jobs and run each exactly once.
  • A failing job is retried after the backoff, then FAILED with its error.
  • A handler that outlives its lease is interrupted, and its worker goes on to the next job.
  • An expired lease is claimed again, and the old worker's late outcome is fenced off.
  • An expired last attempt is FAILED without running the handler again.
  • A handler is not started when claiming used up the lease, or when the queue stopped meanwhile.
  • Starting twice, or stopping and starting again, never runs more than workers jobs at once.
