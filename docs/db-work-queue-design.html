DB Work Queue

Any number of app instances share one Db2 table as a job queue.
A worker leases a row, runs the job, and saves the outcome only if it still holds the lease.

Overview

Producers insert jobs as rows into WORK_ITEM. Each app instance runs workers threads (default 16), and each thread loops: claim a row, run the handler (your job code), save the outcome. Instances share nothing but the table: no broker, no coordinator, no cleanup job.

Five ideas

IdeaWhat it means
ClaimOne statement marks the oldest claimable row CLAIMED and commits at once. Two workers can't claim the same row.
LeaseA claim lasts lease (default 60s); its end time is stored in AVAILABLE_AT. No lock or connection is held while the job runs.
Expiry is recoveryOnce a lease ends, the row is claimable again, so a crashed worker's job reruns without any sweeper. The lease is also the handler's timeout.
FencingEach claim adds 1 to ATTEMPTS. A save applies only if ATTEMPTS still equals the value from the worker's own claim, so after a re-claim it changes nothing.
At-least-onceA job can run twice, for example when a worker crashes after the handler but before the save. Handlers must be idempotent on OPERATION_ID.

AVAILABLE_AT decides what can be claimed

The claim's only filter is AVAILABLE_AT <= CURRENT TIMESTAMP, oldest first. Each write sets it to the next moment the row may be claimed:

WriteSTATUSAVAILABLE_ATSo that
INSERTPENDINGnow, or a later time the producer givesthe job runs at once, or from that time
CLAIMCLAIMEDnow + leaseno one else takes it until the lease ends

Nothing happens when a lease ends. The row still says CLAIMED, but its AVAILABLE_AT is now in the past, so the next claim by any worker takes it. One indexed condition covers new jobs, retries and crash recovery.

The worker loop

Everything a worker does (work() and processNext() in WorkQueue.java):

while running:
    try:
        claimed = processNext()
    catch database error:                    // e.g. Db2 unreachable
        log it; claimed = false
    if not claimed: sleep(poll-interval)

processNext():
    deadline = now + lease                   // worker's own clock, started BEFORE the claim is sent
    job = CLAIM                              // leases at most one row and commits at once
    if no job: return false                  // nothing claimable right now

    if job.attempts > max-attempts:          // the last attempt's lease ran out without an outcome
        FINISH(job, FAILED, "lease expired on the last attempt"); return true
    if not running: return true              // shutting down: row stays CLAIMED until its lease ends
    if now >= deadline: return true          // claiming used the whole lease: same

    start handler(operationId, payload) on a new virtual thread
    wait for it, at most until deadline
    if it is still running:
        interrupt it, then wait for it to stop (no time limit)
        result = failure "handler outlived its lease"

    if handler returned:                     FINISH(job, DONE)
    else if job.attempts < max-attempts:     RETRY(job, error)    // PENDING, claimable after retry-backoff
    else:                                    FINISH(job, FAILED, error)
    return true                              // claim the next job without sleeping
  • Failure: the handler threw anything (Errors included) or timed out. error is the exception's toString(), cut to 300 characters.
  • A save that updates 0 rows lost to a newer claim (see the fence). The worker logs it and moves on.
  • workers is a hard cap. A worker runs one handler at a time and waits for it even after interrupting it.
  • Virtual threads run workers and handlers, so blocking calls don't tie up OS threads. They don't keep the JVM alive, hence spring.main.keep-alive=true.

Starting and stopping

WorkQueue is a Spring SmartLifecycle bean. start() launches the workers at startup. It does nothing if already running, and throws if handlers from a previous run are still alive, so a restart never exceeds workers. stop() runs at shutdown (for example on SIGTERM): it sets running = false, waits up to 30s for handlers, then interrupts the remaining workers and returns. Each interrupted worker interrupts its handler and tries to save a failed attempt. Rows left CLAIMED rerun after their lease.

The three SQL statements

This is all the SQL in WorkQueue.java. Each statement auto-commits on its own.

CLAIM: lease the oldest claimable row

SELECT ID, OPERATION_ID, PAYLOAD, ATTEMPTS FROM FINAL TABLE (
  UPDATE (SELECT ID, OPERATION_ID, PAYLOAD, STATUS, ATTEMPTS, AVAILABLE_AT FROM WORK_ITEM
           WHERE AVAILABLE_AT <= CURRENT TIMESTAMP ORDER BY AVAILABLE_AT FETCH FIRST 1 ROW ONLY)
     SET STATUS = 'CLAIMED', ATTEMPTS = ATTEMPTS + 1,
         AVAILABLE_AT = CURRENT TIMESTAMP + CAST(:lease AS DECIMAL(18, 3)) SECONDS)
SKIP LOCKED DATA

The inner SELECT picks the oldest row whose AVAILABLE_AT has passed. The UPDATE marks it CLAIMED, adds 1 to ATTEMPTS and sets the lease end. FINAL TABLE returns the updated row, so the worker gets its fencing token (the new ATTEMPTS) from the same statement.

Why two workers can't take the same row: the UPDATE locks the row it changes, and SKIP LOCKED DATA makes a competing claim skip that row instead of waiting for it. The claim commits at once; from then on the row's future AVAILABLE_AT keeps it out of every claim until the lease ends. No SELECT … FOR UPDATE is needed, because there is no separate read step to protect.

Requires auto-commit (the default), so the claim commits before the handler starts, and isolation Cursor Stability (the Db2 JDBC default) or Read Stability. Db2 ignores SKIP LOCKED DATA under Uncommitted Read and Repeatable Read (IBM's UPDATE reference).

RETRY: failed, attempts left

UPDATE WORK_ITEM
   SET STATUS = 'PENDING', LAST_ERROR = :error,
       AVAILABLE_AT = CURRENT TIMESTAMP + CAST(:backoff AS DECIMAL(18, 3)) SECONDS
 WHERE ID = :id AND ATTEMPTS = :attempts AND STATUS = 'CLAIMED'

Back to PENDING, claimable after retry-backoff.

FINISH: DONE, or FAILED when attempts are used up

UPDATE WORK_ITEM
   SET STATUS = :status, LAST_ERROR = :error, AVAILABLE_AT = NULL
 WHERE ID = :id AND ATTEMPTS = :attempts AND STATUS = 'CLAIMED'

Final status. AVAILABLE_AT = NULL takes the row out of the queue for good. :error is NULL for DONE.

The fence

Both outcome writes require ATTEMPTS = :attempts, the value this worker's claim returned, and STATUS = 'CLAIMED'. If the lease ran out and another worker re-claimed the row, ATTEMPTS has grown, the write matches 0 rows, and the stale outcome is dropped.

The fence protects the row, not the outside world: the stale handler's downstream effects have already happened. Hence idempotent handlers.

The fence at work: if B wakes up later and saves, its write requires ATTEMPTS = 2. The row has 3, so nothing changes.

Out of attempts: had C crashed too, the first claim after 10:02:34 would set ATTEMPTS = 4, see that 4 exceeds 3, and save FAILED without running the handler. Rows failed this way show ATTEMPTS = max-attempts + 1.

The lease is also the handler's timeout

A lease can't be extended, so the worker must stop the handler before the lease ends. It starts its countdown just before sending the claim; Db2 starts the lease when it runs the claim, slightly later. The worker's deadline therefore always comes first, and the handler gets lease minus the claim's round trip.

  • Handler stops when interrupted: its failed attempt is saved, normally within the lease. A later save still succeeds unless another worker has re-claimed the row.
  • Handler ignores the interrupt: its worker keeps waiting. After Db2's lease ends, another worker may run the same job concurrently; the old worker's save then updates 0 rows.
  • Claiming took the whole lease (slow connection pool or network): the handler isn't started. The row waits out its lease as after a crash, and that attempt is used up.

Run Db2 in UTC. Lease and backoff times use only Db2's clock, so app servers' clocks don't matter. But CURRENT TIMESTAMP is Db2's local time: a daylight-saving jump would end in-progress leases and backoffs up to an hour early (jobs run twice) or late.

What happens when

EventResult
The handler throwsFailed attempt: RETRY after retry-backoff, or FAILED with the error in LAST_ERROR on the last attempt.
The handler runs past the leaseInterrupted; failed attempt with handler outlived its lease.
The handler ignores the interruptIts worker stays busy. After the lease, another worker may rerun the job; the old outcome is fenced off.
An instance crashes or freezesIts rows stay CLAIMED until their leases end, then any worker claims them, using an attempt. If none are left, the row becomes FAILED without running.
Saving DONE fails after the handler succeededThe row stays CLAIMED; the job reruns after the lease.
An instance gets SIGTERMIt stops claiming; handlers get 30s, then are interrupted, which counts as failed attempts.
The database is unreachableWorkers log, sleep poll-interval and retry. A dead connection errors after 30s (blockingReadConnectionTimeout) instead of hanging.
Two workers race for one rowOne gets it; the other skips it and takes the next claimable row.
A producer inserts an OPERATION_ID twiceThe second insert fails with SQLSTATE 23505: already enqueued.

Handlers must time out their downstream calls and stop when interrupted. The queue can interrupt a handler but not force it to stop. If all of an instance's workers are stuck, it stops processing, and other instances take its rows once their leases end. More workers only delay the stall.

Choosing values

lease

Longer than the slowest legitimate job plus the claim. Too short: slow jobs time out on every attempt and end FAILED. Too long: a crashed worker's job waits that long to rerun.

max-attempts × retry-backoff

A job that always fails is FAILED after about (max-attempts − 1) × retry-backoff plus its run times: about 2 minutes by default.

poll-interval

An idle instance sends workers / poll-interval claims per second, 16 by default. Busy workers don't sleep.

Connection pool

A worker holds a connection for one short statement, so Hikari's default pool of 10 is enough for the queue. Add one per worker if handlers share the pool. Waiting for a connection counts against the lease.

Trade-offs and limits

This design replaces an earlier engine (deprecated spec) that renewed leases and ran four background loops besides the workers. Removing them costs:

BeforeNowCost
Lease renewed every 15s while the job runsFixed lease, also the handler's timeoutNo job can run longer than the lease
Fence on CLAIM_TOKEN + OWNERFence on ATTEMPTSNo way to revoke one instance's claims
Sweeper fails expired rows with no attempts leftThe next claim fails themOnly when a worker is free to claim them
Claims in batches of 20One row per claimAn idle instance sends workers / poll-interval claims per second
Supervisor, hung-task limit, liveness probeWait on the handler until the deadline, then interruptA handler that ignores interrupts pins its worker; nothing restarts the instance
Metrics, health, admin API, FlywaySQL queries, schema.sqlMonitoring and migrations are yours to wire up

Both designs rejected bucket ownership with a membership table (rebalancing, skew) and Spring Batch remote partitioning (partitions fixed at step start).

Limits

  • Roughly oldest AVAILABLE_AT first, not FIFO. Retries go to the back; there are no priorities.
  • One lease for every job. Jobs that need a much longer lease need a separate queue.
  • OPERATION_ID holds 64 bytes; PAYLOAD and LAST_ERROR hold 1000 bytes.
  • DONE and FAILED rows stay, recording that an OPERATION_ID was enqueued. Deleting one lets that ID be enqueued again.

Run and check

  1. Apply schema.sql to a Db2 that runs in UTC.
  2. Put your job in the handler lambda in App.java. Return for DONE; throw to retry.
  3. Set SPRING_DATASOURCE_URL, SPRING_DATASOURCE_USERNAME and SPRING_DATASOURCE_PASSWORD.
  4. From db-work-queue, run ./mvnw spring-boot:run (Java 25) on as many machines as you like.

Producers enqueue with INSERT INTO WORK_ITEM (OPERATION_ID, PAYLOAD) VALUES (?, ?).

Check what's in the queue

-- How many rows in each state
SELECT STATUS, COUNT(*) FROM WORK_ITEM GROUP BY STATUS;

-- Jobs that ran out of attempts, and why
SELECT OPERATION_ID, ATTEMPTS, LAST_ERROR FROM WORK_ITEM WHERE STATUS = 'FAILED';

-- How far behind the queue is: when the oldest claimable row became claimable
SELECT MIN(AVAILABLE_AT) FROM WORK_ITEM WHERE AVAILABLE_AT <= CURRENT TIMESTAMP;

-- Expired leases (crashed or stuck workers) waiting to be claimed again
SELECT * FROM WORK_ITEM WHERE STATUS = 'CLAIMED' AND AVAILABLE_AT < CURRENT TIMESTAMP;

What the tests prove

./mvnw test runs against a real Db2 in Docker (a few minutes on Apple Silicon), because the claim relies on SKIP LOCKED DATA.

  • Three instances share 300 jobs and run each exactly once.
  • A failing job is retried after the backoff, then FAILED with its error.
  • A handler that outlives its lease is interrupted, and its worker goes on to the next job.
  • An expired lease is claimed again, and the old worker's late outcome is fenced off.
  • An expired last attempt is FAILED without running the handler again.
  • A handler is not started when claiming used up the lease, or when the queue stopped meanwhile.
  • Starting twice, or stopping and starting again, never runs more than workers jobs at once.
